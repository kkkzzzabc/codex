# 개인용 Codex CLI 포크 운영 지침

이 포크는 업스트림을 유지하면서 개인용 커스텀을 개발하고 사용하는 것을 목적으로 합니다.
공개 배포, 다중 버전 지원, 자동 업스트림 반영은 초기 운영 범위에 포함하지 않습니다.

## 원격과 브랜치

| 이름 | 역할 | 원칙 |
| --- | --- | --- |
| `upstream` | `https://github.com/openai/codex.git` | 업스트림 조회와 가져오기에 사용합니다. |
| `origin` | `https://github.com/kkkzzzabc/codex.git` | 개인용 변경과 복귀 지점을 보관합니다. |
| `main` | 업스트림 원본 보관 | 커스텀을 커밋하지 않고 fast-forward로만 동기화합니다. |
| `codex/custom` | 개인용 커스텀 통합 | 장기 유지하며 업스트림을 merge합니다. |
| `codex/feat/<기능>` | 규모 있는 변경이나 실험 | `codex/custom`에서 생성하고 통합 후 삭제합니다. |
| `codex/sync/YYYYMMDD` | 업스트림 업데이트 검증 | `codex/custom`에서 생성하고 검증·통합 후 삭제합니다. |

기본 브랜치는 `main`으로 유지합니다. 작은 변경은 `codex/custom`에 직접 커밋할 수 있습니다.
PR은 필수가 아니며, 만들 경우 포크 저장소와 대상 브랜치 `codex/custom`을 명시합니다.
공유한 장기 브랜치는 rebase하거나 강제 push하지 않습니다.
동기화 병합 이력은 보존하며 squash하지 않습니다.

## 커스텀 개발

1. 설정, 프롬프트, 스킬, MCP 등 기존 확장 지점으로 요구사항을 해결할 수 있는지 먼저 검토합니다.
2. 소스 수정이 필요하면 목적과 기대 동작, 비교할 기존 동작을 정합니다.
3. 목적이 다른 변경은 별도 커밋으로 나눕니다. 관련 없는 포맷 변경과 이름 변경을 섞지 않습니다.
4. 변경 영역의 검사를 수행하고, 개인 사용에 필요한 동작이 유지되는지 확인합니다.
5. 검증한 커밋은 `origin/codex/custom`에 보관합니다.

커밋 메시지는 scope 없이 영어로 `type: summary` 형식을 사용합니다.
예: `feat: Add custom session filtering`, `fix: Preserve custom settings`, `docs: Document fork maintenance`.

커스텀별로 아래 정보를 기록합니다. 업스트림에 동일 기능이 생기면 제거하거나 통합할지 검토합니다.

| 커스텀 | 목적·기대 동작 | 수정 영역 | 검증 방법·결과 | 제거·통합 조건 |
| --- | --- | --- | --- | --- |
| 개인용 운영·빌드 도구 | 작은 용량의 격리 환경에서 빌드를 재현합니다. | `AGENTS.md`, `scripts/build-personal-package.sh`, 이 문서 | 래퍼 구문 검사와 드라이런을 확인합니다. 기존 도구의 패키지 빌드 실측은 아래에 기록합니다. | 업스트림이 같은 운영 방식을 제공하면 통합을 검토합니다. |

## 업스트림 반영

필요한 기능이나 버그 수정이 있을 때, 또는 정기 검토 시 업스트림 반영 여부를 판단합니다.
`main` 동기화와 실제 사용하는 커스텀 버전 업데이트는 별도로 진행합니다.
업스트림 `main` 또는 정식 릴리스 태그 중 반영할 지점을 선택하고 정확한 SHA를 기록합니다.

1. 미커밋 변경이 없는지 확인합니다. 작업 중인 변경이 있으면 먼저 정리합니다.
2. 정상 동작이 확인된 커스텀 커밋에 `custom-good-YYYYMMDD-01` 같은 고유 태그를 남깁니다.
   태그는 재사용하거나 이동하지 않습니다. 현재 사용하는 실행 파일도 별도로 보관합니다.
3. 업스트림을 가져오고 `main`을 fast-forward로 동기화합니다. 분기된 이력이 있으면 원인을 확인합니다.
4. `codex/custom`에서 동기화 브랜치를 생성하고 선택한 업스트림 SHA를 merge합니다.
5. 충돌은 커스텀 요구사항과 업스트림 변경 의도를 함께 확인하여 해결합니다.
6. 검증에 통과하면 동기화 브랜치를 `codex/custom`으로 fast-forward 통합합니다.
   검증 중 `codex/custom`이 변경됐다면 최신 커스텀을 동기화 브랜치에 합친 뒤 다시 검증합니다.
7. 기준 SHA와 검증 결과를 이 문서에 기록하고, 브랜치와 복귀용 태그를 `origin`에 보관합니다.
8. 통합·원격 보관이 끝난 임시 브랜치를 삭제합니다.

아래 명령은 저장소 루트에서 단계별로 실행하는 예시입니다. SHA와 브랜치 이름은 실제 값으로 바꿉니다.
충돌이나 오류가 발생하면 다음 단계로 진행하지 않습니다.

```bash
git status --short --branch
git fetch --no-tags upstream refs/heads/main:refs/remotes/upstream/main
git switch main
git merge --ff-only upstream/main
git push origin main

git switch codex/custom
git switch -c codex/sync/YYYYMMDD
git merge --no-ff <selected-upstream-sha> -m "chore: Merge upstream updates"

# 충돌 해결과 검증을 완료한 뒤 실행합니다.
git switch codex/custom
git merge --ff-only codex/sync/YYYYMMDD
git push origin codex/custom
```

정식 릴리스 태그를 선택할 때는 해당 태그를 별도로 가져옵니다.
정상 버전 태그는 `git push origin <tag>`로 개별 보관합니다.
업스트림 태그를 일괄 push하지 않습니다. 기존 배포 자동화는 `rust-v*.*.*` 태그에 반응할 수 있습니다.

## 검증 기준

- 변경 전후를 같은 요구사항과 기대값으로 비교합니다.
- 기능 변경은 관련 포맷·정적 검사와 변경한 crate의 테스트를 확인합니다.
- 동기화는 커스텀 기능과 업스트림 변경의 영향 영역을 함께 검사합니다.
- 기존 검사 방법은 루트 `justfile`과 `docs/install.md`에서 확인합니다.
  `just fmt-check`, `just clippy -p <crate>`, `just test -p <crate>` 등을 변경 범위에 맞게 선택합니다.
- 프로그램 실행을 수반하는 빌드·테스트·CLI 확인은 목적과 범위를 설명하고 사용자 승인을 받은 뒤 수행합니다.
  파일·설정·상태 조회는 직접 진행합니다.
- 실패한 검사를 삭제하거나 건너뛰거나 기준을 낮추지 않습니다.
- 수행한 검사, 확인하지 않은 사항과 그 이유를 구분하여 기록합니다.

## 설치와 복귀

공식 설치본과 커스텀 설치본은 실행 경로 또는 실행 명령을 구분합니다.
공식 자동 업데이트가 커스텀 실행 파일을 덮어쓰지 않도록 별도 위치를 사용합니다.
초기에는 로컬 빌드만 사용하며 별도 패키지 배포나 서명 체계를 도입하지 않습니다.

업데이트 검증이 실패하면 통합을 보류하고 기존 정상 실행 파일을 계속 사용합니다.
복귀 태그에서 소스를 다시 빌드할 경우 현재 커스텀 브랜치를 reset하지 않고 별도 작업 공간을 사용합니다.
태그는 소스의 복귀 지점이며 실행 파일이나 세션 데이터를 복원하지 않습니다.
세션·설정 저장 형식에 영향을 주는 변경은 데이터 백업과 별도 저장 경로를 함께 검토합니다.

## 최소 빌드 환경과 실행

개인용 빌드는 [빌드 래퍼](../scripts/build-personal-package.sh)를 사용합니다.
이 래퍼는 기존 패키지 구성 도구를 호출하며, 측정 폴더의 임시 래퍼나 `just`가 필요하지 않습니다.
macOS arm64와 Python 3.11 이상이 필요합니다. 최초 검증은 Rust 1.95.0과 Python 3.12.15를 사용했습니다.
Rust 버전은 `codex-rs/rust-toolchain.toml`에서 읽으므로 업스트림 반영 후에는 필요한 toolchain도 확인합니다.

준비 방법은 환경 관리 폴더의 `utilities/environment-setup/README.md`에 있습니다.
공통 패키지는 dotfiles의 Brewfile에서 관리하고, 프로젝트별 버전과 빌드 방식은 이 저장소에서 관리합니다.
래퍼는 도구를 자동 설치하지 않습니다. Rust·Python 경로를 확인한 뒤 실행합니다.

작업 폴더는 저장소 밖에 두며 다음 구조를 사용합니다.

| 경로 | 용도 |
| --- | --- |
| `tools/rustup/` | 프로젝트 toolchain을 보관하는 `RUSTUP_HOME` |
| `tools/python/` | `uv`로 준비한 별도 Python |
| `deps/cargo/` | Cargo 의존성 캐시인 `CARGO_HOME` |
| `target/` | 재사용 가능한 빌드 결과 |
| `tmp/` | V8·보조 리소스 캐시와 임시 파일 |
| `packages/<시각>/` | 새 실행 패키지 |

기존 실측 환경은 `$HOME/.cache/codex-min-build/20261006-171955`에 있습니다.
새 환경을 만들기 전에 이 환경을 재사용할지 확인합니다. 환경을 여러 개 만들면 toolchain과 캐시가 중복됩니다.
실측 당시의 산출물은 이 폴더의 `package/`에 보존되어 있으며, 래퍼의 새 산출물은 `packages/` 아래에 생성됩니다.

저장소 루트에서 아래와 같이 드라이런으로 명령을 확인합니다.

```bash
work_dir="$HOME/.cache/codex-min-build/20261006-171955"
python_bin="$work_dir/tools/python/cpython-3.12.15-macos-aarch64-none/bin/python3.12"

./scripts/build-personal-package.sh \
  --work-dir "$work_dir" \
  --python "$python_bin" \
  --dry-run
```

실제 빌드를 승인받은 뒤 같은 명령에서 `--dry-run`만 제거합니다.
기본 출력 경로는 `WORK/packages/<UTC 시각>`이며, `--package-dir`로 그 아래의 새 경로를 지정할 수도 있습니다.
`--rustup`은 실행 파일 경로를 지정합니다. 생략하면 PATH와 Homebrew 기본 위치를 순서대로 확인합니다.
드라이런은 도구 경로와 Python 요구사항을 확인하고 명령만 출력하며, 파일 생성·다운로드·컴파일을 하지 않습니다.

빌드 설정은 macOS arm64, `dev-small`, 증분 캐시 끔, 병렬 작업 2개, Cargo `--locked`입니다.
V8는 사전 빌드 파일을 사용하고 CLI와 필수 `codex-code-mode-host`만 빌드합니다.
래퍼는 전역 셸·Rust 기본 설정을 바꾸거나 기존 패키지를 덮어쓰거나 파일을 삭제하지 않습니다.
테스트, release 빌드, CLI 실행, 압축 아카이브 생성도 하지 않습니다.

기존 측정 도구가 제공한 5초 간격 디스크 감시는 이 래퍼에 포함되지 않습니다.
래퍼에는 자원 감시 기능이 없으므로 장시간 빌드에서는 디스크 여유를 별도로 확인합니다.
실행 실패 시 출력과 부분 결과를 보존하고 원인을 확인합니다. 래퍼는 별도 로그 파일을 자동 생성하지 않습니다.
실패를 숨기거나 잠금 파일을 자동 갱신하지 않습니다.

## 용량과 보관 정책

빌드 환경 전체와 패키지 용량을 구분합니다. 용량은 버전·변경 범위·빌드 설정에 따라 달라집니다.
아래 측정값을 향후 빌드의 보장값으로 사용하지 않습니다.

- `packages/`의 정상 패키지와 실측 당시 `package/`는 캐시 정리와 별도로 보존합니다.
- `target/`을 정리하면 재컴파일이 필요하지만 실행 패키지는 유지됩니다.
- `deps/cargo/`는 재빌드를 위한 다운로드·소스 캐시입니다. 정리하면 다시 다운로드합니다.
- `tools/rustup/`과 `tools/python/`은 빌드 도구이므로 다시 빌드할 계획이면 보관합니다.
- `tmp/`와 다운로드 캐시는 재생성할 수 있지만 다음 작업에서 다시 다운로드할 수 있습니다.
- 정리는 대상 경로와 예상 영향, 보존할 패키지를 확인한 뒤 승인된 범위에서 수행합니다. 전체 작업 폴더를 일괄 삭제하지 않습니다.
- 용량 재측정은 전체 파일 조회가 필요하므로 회의 중 등 자원 제한이 있을 때는 수행하지 않습니다.
